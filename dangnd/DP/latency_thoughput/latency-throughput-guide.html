Latency & Throughput

A Visual Guide for Distributed System Design

This document explains two important performance measures: Latency and Throughput. These measures have a strong mathematical relationship. If you change one, the other also changes.

About this document: The text follows ASD-STE100 (Simplified Technical English) rules — short sentences, approved words, active voice, and clear structure.

1 — Core Definitions

⏱ Latency

Latency is the total time for one request to go through the system. It starts when the client sends the request. It ends when the client gets the response.

Unit: milliseconds (ms)

Lower is better.

📊 Throughput

Throughput is the number of requests that the system completes in one unit of time. A high throughput means that the system does more work.

Unit: requests/second (rps)

Higher is better.

3 — Throughput: What Limits It

The throughput of a system is always limited by its slowest component (the bottleneck).

⚠ Key rule: System throughput = throughput of the slowest component. In this example, the database limits the whole system to 1,000 rps.

4 — The Relationship Between Latency and Throughput

Latency and throughput are not independent. They are connected through queueing theory and concurrency limits.

💡 Key insight: At low load, latency is almost flat. But as utilization goes above ~70%, latency increases with a non-linear (hyperbolic) curve. At the same time, throughput stops to increase and then decreases because of contention.

5 — Little's Law

John D.C. Little proved this law in 1961. It connects three important measures of any stable system.

L = λ × W L = concurrent requests in system  |  λ = throughput (rps)  |  W = average latency (sec)
Universality: This law is always correct. It does not depend on the arrival pattern, the service time pattern, or the queue order. It works for CPU, database, network, disk I/O, message queues, and even a checkout line at a supermarket.

Where does Little's Law apply?

Example Calculation

A service processes 1,000 requests/second with an average latency of 200 ms.

6 — Queueing Theory

6.1 Utilization Law

When you apply Little's Law only to the processing part (not the queue), you get the Utilization Law:

ρ = λ × S ρ = utilization (0 to 1)  |  λ = throughput  |  S = service time

6.3 The Hockey-Stick Effect

Latency does not increase at a steady rate. It follows a hyperbolic curve. When utilization approaches 100%, latency goes to infinity.

6.5 M/G/1 — Variable Service Times

In the real world, service times are not the same for all requests. Some queries are fast, some are slow. The coefficient of variation (C = σ / μ) measures this variability.

UPI = C² × ρ ÷ (1 − ρ) UPI = Unit Performance Index  |  C = coefficient of variation  |  ρ = utilization
⚠ Important: When C is high (variable workloads), the latency explosion happens much earlier. For example, with C = 2, latency at 50% utilization is already 4× the service time — the same as 80% utilization in the M/M/1 model.

8 — Design Trade-offs

You cannot maximize throughput and minimize latency at the same time. There is always a trade-off.

Low-Latency Design

  • Keep utilization below 50–70%
  • Use in-memory caches
  • Reduce hops between services
  • Co-locate services in the same region
  • Use connection pooling

Example: Real-time trading, gaming, video calls

High-Throughput Design

  • Batch requests together
  • Use asynchronous processing
  • Increase parallelism (more workers)
  • Use message queues for decoupling
  • Accept higher latency for individual requests

Example: Data pipelines, log processing, batch ETL

When can you optimize both?

You can improve both only if you remove the bottleneck. This usually means:

  • Better algorithms (lower S → lower ρ → lower R → higher λ possible)
  • Better hardware (faster CPU, SSD instead of HDD)
  • Caching (bypass the bottleneck completely)
  • Data locality (reduce network hops)

9 — Best Practices Summary

💡 The Golden Rule: A sustainable distributed system does not try to eliminate latency or push throughput beyond the hardware limit. Instead, it keeps the system in a dynamic balance — left of the saturation point — where Goodput stays high and tail latency stays predictable.
