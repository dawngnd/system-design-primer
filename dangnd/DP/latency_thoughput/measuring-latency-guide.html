Measuring Latency

A practical guide to percentiles, distributions, and why averages lie.

1 — The Problem With Averages

An average hides the detail. It takes all values and puts them into one number. You cannot see the shape of the data.

Service A — Stable

48 49 50 50 51 51 52 52 53 54

Average51 ms
P9554 ms
Spread48 – 54 ms (narrow)

✅ All users have a good experience.

Service B — Long tail

10 11 11 12 12 12 13 14 15 390

Average50 ms
P95390 ms
Spread10 – 390 ms (wide!)

❌ 1 in 10 users waits 390ms. Average hides this.

⚠ Key insight: Both services show an average of ~50ms. But the user experience is completely different. The average gives the same score to a healthy system and a sick system.

2 — Latency Distributions

In queueing theory, the M/M/1 model uses an exponential distribution for service times. In the real world, latency usually follows a log-normal or multi-modal distribution — most requests are fast, but a long tail of slow requests exists.

2.1 — Normal vs Long-Tail Distribution

Normal (Gaussian)

Symmetric. Average ≈ median. Few outliers. Rare in latency data.

Long-Tail (Log-normal)

Skewed right. Average > median. Many outliers. Common in real latency data.

2.2 — Why Does the Long Tail Exist?

CauseEffect on LatencyFrequency
Garbage Collection (GC pause)+50ms to +500ms spikeEvery ~100–1000 requests
Cache miss → database query+10ms to +200ms1–10% of requests
TCP retransmission+200ms to +3000ms0.1–1% of packets
Context switch / CPU throttle+5ms to +50msUnder high load
Lock contention+10ms to +500msUnder concurrency
Cold start (serverless/container)+500ms to +5000msFirst request after idle
Cross-region call+60ms to +200msIf routing changes
💡 Connection to M/M/1: The exponential service time in M/M/1 already produces a long tail — the probability of a very long service time is small but never zero. Real systems are worse because multiple causes (GC, cache miss, retransmit) stack on top of each other.

3 — Percentiles: P50, P95, P99

3.1 — What is a Percentile?

Sort all latency values from lowest to highest. The PN value is the point where N% of requests are faster.

3.2 — What Each Percentile Tells You

MetricMeaningMonitoring RoleWho is affected
P50 The median. Half of requests are faster than this value. Shows the typical user experience. The "average" user
P95 Only 5% of requests are slower. Early warning — degradation has spread to many users. 1 in 20 users
P99 Only 1% of requests are slower. Smoke detector — finds problems before they spread. 1 in 100 users
P99.9 Only 0.1% of requests are slower. Catches extreme outliers. Used in payment / trading systems. 1 in 1,000 users

3.3 — P95 vs P99: Different Detection Capabilities

Scenario comparison — same system, different failure modes:

ScenarioAffected %P95 detects?P99 detects?
GC pause (1 in 100 req)1% ❌ No — below 5% threshold ✅ Yes — exactly at 1%
DB pool exhaustion (10% of req)10% ✅ Yes — above 5% ✅ Yes
Gradual memory leakGrows over time ⏳ Detects late (hour 4) ⚡ Detects early (hour 2)
Network partition (30%)30% ✅ Yes — severe ✅ Yes — severe

5 — The Fan-out Amplification Problem

Modern systems call many services to build one response. The total latency is the slowest of all calls. This makes tail latency much worse.

P(all fast) = 0.99N N = number of service calls in the critical path
Services (N)P(all under P99)% requests hitting ≥1 slow callImpact at 1M req/day
199.0%1.0%10,000 slow
397.0%3.0%30,000 slow
595.1%4.9%49,000 slow

2081.8%18.2%182,000 slow

💡 Lesson: With fan-out, the P99 of the whole system is much worse than the P99 of any single service. This is why large-scale systems (Google, Amazon) focus heavily on tail latency.

7 — Common Measurement Pitfalls

❌ Pitfall 1: Averaging percentiles across instances

You have 3 servers. Each reports P99 = 80ms, 120ms, 300ms. The average of these three P99 values is 167ms. But this is wrong!

You must merge all raw data first, then calculate one P99 from the combined set. The correct P99 of the combined data could be much higher than 167ms.

Rule: Never average percentiles. Merge first, then calculate.
❌ Pitfall 2: Coordinated omission

Most load test tools send the next request only after the previous one completes. When the server is slow, the tool sends fewer requests. The slow period is underrepresented in the data.

Result: The measured P99 looks better than reality.

Fix: Use tools that send requests at a fixed rate regardless of responses — for example, wrk2 or Gatling with open-model.
❌ Pitfall 3: Too few samples

To get a meaningful P99, you need at least 1,000 samples (so the "1%" is at least 10 data points). For P99.9, you need 10,000+ samples.

PercentileMin samples for 1 data point in tailRecommended samples
P9520500+

❌ Pitfall 4: Client-side vs server-side measurement

Server-side latency does not include network time or client queue time. Always measure from the client perspective when possible.
